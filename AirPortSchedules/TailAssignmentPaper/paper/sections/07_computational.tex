\subsection{Implementation and environment}

All models are implemented in Python~3.10+ using the Pyomo optimisation
framework~\citep{pyomo2023}. The compact benchmark in Table~\ref{tab:repro5}
and the matched diagnostic in Table~\ref{tab:matched_stress} were solved with IBM ILOG
CPLEX~\citep{cplex2023} through Pyomo's \texttt{cplex} shell backend. For the
new Constraint~(13) verification and per-check-type hierarchy study
(\Cref{subsec:comp_c13,subsec:hierarchy_results}) results are cross-validated
with two independent exact MILP solvers: the open-source HiGHS
solver~\citep{highs2023} through Pyomo's \texttt{appsi\_highs} interface, and
the full, unrestricted IBM ILOG CPLEX~12.6 build distributed with AMPL
through Pyomo's \texttt{cplexamp} ASL interface. The CPLEX copy already on
this machine's PATH is a size-restricted Community/Preview edition (1\,000
variable/constraint limit) that raises \texttt{CPLEX Error 1016} on every
instance in this study once maintenance constraints are included; it is not
used for any reported result. HiGHS and the unrestricted CPLEX build agree
exactly (same status, same objective) on every instance reported in
\Cref{subsec:hierarchy_results}, giving solver-independent confidence in the
correctness claims.
The code, instance generator, and experiment runner are publicly available at
the companion repository.

\paragraph{Comparison protocol.}
The compact benchmark and the matched diagnostic use the same JSON instances
and assignment-cost data for both formulations where a comparison is claimed.
They do not by themselves certify cumulative-hour correctness;
\Cref{subsec:comp_c13,subsec:hierarchy_results} evaluates the real built
constraints and independently replays maintenance counters.

\subsection{Instance generation}

The current generator creates deterministic synthetic instances. For
parameters $(\delta,n_p,n_d)$ it generates approximately
$\delta n_p n_d$ flights, chooses airports and times from seeded pseudo-random
distributions, and uses a stable seed for each test index. Thus $\delta$ is a
flight-count scaling parameter in this repository, not the fleet-to-minimum-
fleet ratio used by \citet{khaled2018compact}. Unless a table states otherwise,
the quick snapshots contain one generated instance per parameter cell.

\subsection{Measured effectiveness of the ordered event formulation}
\label{subsec:event_measurements}

\Cref{sec:event_reformulation} proves the standalone event-based reformulation exact
and immune to the endpoint-split failure mode by construction. This
subsection measures the latest ordered implementation's practical behavior against the day-indexed
legacy model on which it improves, using
\texttt{experiments/compare\_formulations.py}. While diagnosing the first
solved comparisons below, the same protocol used to certify results
elsewhere in this section -- always cross-checking a status against an
independent computation -- exposed an implementation defect in
\texttt{src/event\_model.py}: the pre-horizon initial-hours constraint used
a big-$M$ equal to the source flight's own duration plus its initial hours,
which is not a valid upper bound on $u_{ijk}$ once a route has accumulated
several flights, and made the model reject cost-optimal schedules it should
accept. The fix (using $T_k+p_i$, the same bound family as
\Cref{eq:event_c12}) is included in the code accompanying this paper; all
results below use the corrected version.

\paragraph{Solved comparison on a well-posed instance.}
On a small hand-built instance with two aircraft, six flights, and a
threshold comfortably above the total flying time
(\texttt{data/instances/event\_vs\_legacy\_clean\_test.json}), both
formulations now return the same optimal objective (600, a single aircraft
covering all six flights with no maintenance event), using CPLEX 12.6 for
AMPL as the solver of record. This is exact agreement between two
independently coded formulations on a genuinely solved instance, not merely
a build-time comparison.

\paragraph{A modelling-convention gap on the existing ABCD suite.}
On the existing \texttt{ABCD\_*} boundary instances
(for example \texttt{ABCD\_capacity\_bottleneck\_test}), the event-based
model reports \texttt{infeasible} where the legacy model reports
\texttt{optimal}. This is
not a solver or implementation defect: these instances' own design notes
(e.g. \texttt{ABCD\_capacity\_bottleneck\_test.json}) state that an aircraft
is intended to fly \emph{past} its hour threshold and only be checked that
same night -- exactly the permissive convention encoded in the legacy
model's C13b relaxation. The exact-state formulations of this paper (both
the day-indexed recursion of \Cref{subsec:c13_state} and the event-based
\Cref{eq:event_c11} bound $u_{ijk}\le T_k x_{ij}$ unconditionally) instead
require the threshold to never be exceeded at any arrival, check or no
check. Under that stricter, arguably safer reading, these particular
instances are genuinely infeasible: no schedule exists in which an aircraft
never exceeds its hour limit for these initial states and flight durations.
This is a modelling-convention gap between the existing benchmark suite and
the corrected formulations of this paper, not a defect in either
implementation, and it is a direct practical consequence of fixing the
endpoint-split flaw: the corrected model can no longer quietly accept the
same after-the-fact resolution the legacy convention relied on.

The variable-count advantage predicted by
\Cref{tab:event_variable_counts} holds at $h=7,15,21$ (27--36\% fewer
variables) but reverses at $h=30$, where the event model uses 20\% \emph{more}
variables. Constraint count is larger for the event-based model at every
horizon tested, by a factor of 1.6--2.8, and this factor broadly increases
with $h$. The
reason is exactly the caveat already noted in
\Cref{sec:event_reformulation}: constraint~\eqref{eq:event_c12} is built over
every feasible connection $(i,\ell)\in\Conn$, and $|\Conn|$ grows
super-linearly with the number of flights on these dense
($\delta=1.0$) synthetic instances, whereas the legacy model's maintenance
constraint count scales with $n_pn_d$. The event-based reformulation is
therefore not unconditionally smaller in practice: its variable-count
advantage is real but bounded, and its constraint count is measurably larger
on this benchmark family, a genuine trade-off rather than a strict
improvement.

An exploratory density-0.5 horizon stress run is retained in the companion
repository as \texttt{results/tables/formulation\_horizon\_scaling.csv}, but
is excluded from runtime claims because its infeasible and time-limited rows
mix different feasible domains. The corrected independent replay also showed
that the legacy endpoint-split optimum on the h=10 exploratory instance can
violate the A/B flight-hour state limits. The controlled runtime comparison
below therefore uses only feasible heavy instances for which both formulations
are optimal and objective-matched.

The matched stress comparison also uncovered and corrected an objective-model
defect in the legacy implementation. The day-indexed model represents a
multi-day check by consecutive occupancy variables and previously charged a
flat penalty per occupied day. When a check extended beyond the planning
horizon, this underpriced the event relative to the event formulation, which
charges once per check using its full duration. The legacy model now includes
an explicit binary maintenance-start variable and charges the same
duration-based event cost as the event formulation. After this correction, the
$h=21$ heavy case has objective $881\,263$ in both formulations; the corrected
matched result is recorded in
\texttt{results/tables/formulation\_h21\_objective\_aligned\_v2.csv}.

Both formulations are exact, so any solved-objective comparison between them
is only informative on instances that are actually feasible; the random
\texttt{DataCplex} generator can produce infeasible cells at higher densities,

property of either formulation. \texttt{src/generate\_feasible\_instances.py} instead builds

\paragraph{A second implementation defect, found and fixed the same way.}
The same generator, run with \texttt{--maintenance-families ABCD}, initially
solved under the legacy model but returned \texttt{infeasible} under the
event-based model. Applying the same fault-isolation procedure used for
\Cref{eq:event_c13} (relax all binary variables, solve the LP, and
deactivate one named constraint block at a time) to
constraints~\eqref{eq:event_c14a}--\eqref{eq:event_c14b} found a second,
distinct defect: the candidate set for a calendar-check deadline was built
from \emph{cost-feasible} assignment arcs only, without checking whether the
candidate flight is actually \emph{reachable} by that aircraft's route (a
flight can be affordable for an aircraft under the cost matrix's ferry
penalty while having no predecessor path to it at all in this sparse
hub-and-spoke instance family). The deadline constraint could then require a
check on a flight the aircraft could never legally reach, an unsatisfiable
requirement masquerading as a routing infeasibility. A second, narrower
defect surfaced during the fix: the placeholder row inserted when no
candidate exists at all evaluated to a plain Python \texttt{False} instead
of a symbolic Pyomo constraint, raising a solver-side error rather than a
clean infeasible status. Both are fixed in the code accompanying this
paper (an explicit reachability check via the same predecessor sets used by
constraint~\eqref{eq:event_c2}, and a placeholder anchored on a real
variable). Root-causing the resulting failure on the regenerated instance
traced to a third defect, this time in the instance generator itself: the
calendar-check deadline slack was computed from the coarse departure-day
index rather than the outbound flight's actual arrival time, so the
day-rounding in \texttt{src/generate\_feasible\_instances.py} could place an
aircraft's own designated check-triggering flight a few minutes past its own
deadline. With all three fixes applied, the regenerated ABCD instance
solves \texttt{optimal} under both formulations with the identical objective
(10\,327), completing the cross-validation started above. We report the
diagnostic process itself, not only the fix, because it is the same
generic technique (LP relaxation plus single-block deactivation) used
earlier for Constraint~(13), applied here to a different constraint family
with a different, unrelated root cause.

\subsection{Calendar candidate pruning in the newest ordered profile}
\label{subsec:ordered_calendar_pruning}

The latest full-ABCD ordered profile used for final horizon measurements in
this paper is:
\begin{itemize}
  \item interval-clique overlap rows,
  \item tightened state big-$M$ constants,
  \item aircraft-local state indexing, and
  \item calendar candidate pruning in C14 windows.
\end{itemize}

calendar window by aggregating candidates at the flight level before building
C14 rows. This is semantics-preserving under the model's

\subsection{Summary of findings}

\begin{enumerate}
  \item The current runs validate the corrected formulations on deterministic
    synthetic instances; they do not reproduce the published data or
    averages.
  \item The Constraint~(13) endpoint-split flaw of \Cref{lem:c13_split_limit}
    is confirmed computationally: all 42 real constraint rows built by
    \texttt{src/model.py} for the loophole instance are satisfied at an
    adversarial point where 1\,200 minutes are actually flown against a
    600-minute limit, while the exact-state recursion correctly rejects it.
  \item Solved in isolation, each of the four check types (A, B, C, D) is
    enforced correctly by the legacy hierarchy model on
    \texttt{ABCD\_near\_threshold\_test}: optimal, fully covered, and
    independently validated with zero violations.
  \item Under the full mixed hierarchy, the same flaw reappears
    unprompted on an existing test instance (aircraft~2 in
    \texttt{ABCD\_check\_hierarchy\_test} exceeds its A-check threshold by
    200 minutes with no violated constraint reported), showing the issue is
    not confined to hand-built corner cases.
  \item The correctness comparison shows that the event formulation rejects
    both adversarial C13 violations, while the original paper row and the
    endpoint-split legacy formulation each fail on one complementary pattern.
  \item After correcting legacy multi-day maintenance-event pricing, the
    legacy and event formulations reach identical objectives on all three
    feasible heavy instances reported in Table~\ref{tab:matched_stress}.
  \item Historical boundary cases that depend on after-threshold checking are
    excluded from the correctness comparison because they use a different
    maintenance convention; dense exploratory cases remain solver diagnostics.
  \item The latest ordered-model speed optimizations (clique overlap +
    tightened state big-$M$) are solver-dependent: they improve CPLEX on
    average (+5.26\% wall-time gain on the tested horizon grid) but degrade
    HiGHS on average (-12.32\%), so solver-specific profile defaults are
    required for fair runtime reporting.
  \item In the latest A-only benchmark, the ordered A-event implementation is
    consistently faster than the legacy A-only model across all tested
    horizons, with mean gains of +18.70\% wall time and +14.73\% CPU time.
  \item Adding calendar candidate pruning to the newest ordered ABCD profile
    gives a small but consistent additional gain on the tested horizon family
    (+0.12\% mean CPU, +0.22\% mean wall) while preserving optimal status and
    objective parity in every run.
  \item This environment contains both a PATH-restricted CPLEX build and an
    unrestricted CPLEX~12.6-for-AMPL executable; all reported CPLEX runtime
    results in this section use the unrestricted solver path.
\end{enumerate}

\subsection{Phase 2: Structural trial of event-based maintenance bridge modes}
