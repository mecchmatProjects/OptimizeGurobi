\section{Computational Study}
\label{sec:computational}
%%==========================================================================

\subsection{Implementation and environment}

All models are implemented in Python~3.10+ using the Pyomo optimisation
framework~\citep{pyomo2023}. Earlier snapshot runs (Tables~\ref{tab:repro5}--\ref{tab:repro11},
\ref{tab:boundary_suite}--\ref{tab:dense_heavy_suite}) were solved with IBM ILOG
CPLEX~\citep{cplex2023} through Pyomo's \texttt{cplex} shell backend. For the
new Constraint~(13) verification and per-check-type hierarchy study
(\Cref{subsec:comp_c13,subsec:hierarchy_results}) results are cross-validated
with two independent exact MILP solvers: the open-source HiGHS
solver~\citep{highs2023} through Pyomo's \texttt{appsi\_highs} interface, and
the full, unrestricted IBM ILOG CPLEX~12.6 build distributed with AMPL
through Pyomo's \texttt{cplexamp} ASL interface. The CPLEX copy already on
this machine's PATH is a size-restricted Community/Preview edition (1\,000
variable/constraint limit) that raises \texttt{CPLEX Error 1016} on every
instance in this study once maintenance constraints are included; it is not
used for any reported result. HiGHS and the unrestricted CPLEX build agree
exactly (same status, same objective) on every instance reported in
\Cref{subsec:hierarchy_results}, giving solver-independent confidence in the
correctness claims.
The code, instance generator, and experiment runner are publicly available at
the companion repository.

\paragraph{Comparison protocol.}
The reported legacy-MILP snapshot tables (Tables~\ref{tab:repro5}--\ref{tab:dense_heavy_suite})
use the same JSON instances and assignment-cost data and only compare
solutions with equal flight coverage; they were produced before the
endpoint-split flaw was isolated and do not by themselves certify
cumulative-hour correctness. \Cref{subsec:comp_c13,subsec:hierarchy_results}
supersede these snapshots for the Constraint~(13) question: they evaluate the
real built constraints and independently replay every solved schedule's
maintenance counters, rather than trusting the solver's own feasibility
report.

\subsection{Instance generation}

The current generator creates deterministic synthetic instances. For
parameters $(\delta,n_p,n_d)$ it generates approximately
$\delta n_p n_d$ flights, chooses airports and times from seeded pseudo-random
distributions, and uses a stable seed for each test index. Thus $\delta$ is a
flight-count scaling parameter in this repository, not the fleet-to-minimum-
fleet ratio used by \citet{khaled2018compact}. Unless a table states otherwise,
the quick snapshots contain one generated instance per parameter cell.

\subsection{Numeric verification of the Constraint~(13) endpoint-split flaw}
\label{subsec:comp_c13}

Lemmas~\ref{lem:c13_flaw} and~\ref{lem:c13_split_limit} are proved
algebraically in \Cref{subsec:c13_flaw,subsec:c13_corrected}. We additionally
verify both directly against the production implementation:
\texttt{experiments/c13\_loophole\_validation.py} builds the real
\texttt{LegacyEndpointSplitMILPScheduler} model -- with both the split
formulation and, using the restored \texttt{use\_paper\_c13} toggle, the
original Khaled et al. (2018) form -- on the four-day, single-aircraft
instance \texttt{data/instances/c13\_loophole\_test.json}
($T^A_{\max}=600$~min, $600$~min flown on each of days~2 and~4), and
evaluates every real \texttt{m.c13} constraint row at two adversarial check
patterns.

\centering\small
\caption{Numeric verification of Lemmas~\ref{lem:c13_flaw}
  and~\ref{lem:c13_split_limit} against the real \texttt{m.c13} constraints
  (both formulations) and the exact-state recursion
  (\texttt{results/tables/c13\_loophole\_validation.csv}). Both scenarios fly
  1\,200 real minutes in window $(1,4]$ against $T^A_{\max}=600$.}
\label{tab:c13_loophole}
\begin{tabular}{lccc}
\toprule
Check pattern & Split C13 & Paper C13 & Exact-state \\
\midrule
Both endpoints checked (days 1, 4) & \textbf{accepts (wrong)} & rejects (correct) & rejects \\

\bottomrule

\Cref{tab:c13_loophole} confirms both lemmas computationally, and shows the
two formulations fail in \emph{complementary, non-overlapping} cases, exactly
as predicted in \Cref{subsec:c13_corrected}: when checks occur at both
window endpoints, all 42 real split rows are satisfied even though 1\,200
minutes are flown against the 600-minute limit (Lemma~\ref{lem:c13_split_limit}),
while the single paper-form row correctly rejects it. When only the end day
is checked, the paper form's single row is satisfied despite the same
1\,200-minute violation (Lemma~\ref{lem:c13_flaw}), while all 42 split rows
correctly reject it (one row is violated). In both scenarios the exact-state
recursion \eqref{eq:c13_state_lower}--\eqref{eq:c13_state_bound}, evaluated on
the same flight and check data, correctly flags the violation. This is a
computational proof, not merely an algebraic one: the values above come from
evaluating the actual Pyomo constraint objects built by
\texttt{src/model.py}, with its real $M_{\text{BIG}}=9\,999\,999$ constant,
rather than a hand re-derivation of the inequalities.

\subsection{Full hierarchy results and per-check-type effectiveness}
\label{subsec:hierarchy_results}

\Cref{tab:hierarchy} reports \texttt{experiments/hierarchy\_effectiveness.py}:
for each check type in isolation (A, B, C, D) we solve the legacy
endpoint-split MILP on \texttt{ABCD\_near\_threshold\_test}, and for the
full mixed hierarchy on \texttt{ABCD\_check\_hierarchy\_test}. Results are
cross-validated with two independent exact solvers: the open-source HiGHS
solver (\texttt{appsi\_highs}) and the full, unrestricted IBM ILOG CPLEX 12.6
build distributed with AMPL (invoked through Pyomo's \texttt{cplexamp} ASL
interface); both report identical objectives and statuses on every instance
in this study. The CPLEX copy already on this machine's PATH is a
size-restricted Community/Preview edition (1\,000 variable/constraint limit,
\texttt{CPLEX Error 1016}) that cannot solve any instance with maintenance
constraints active; it is not used for any reported result. Every solved
instance is independently re-verified by replaying its solution: hour-triggered
checks (A, B) are checked with the
exact-state recursion of \Cref{subsec:c13_state}, and calendar-triggered
checks (C, D) are checked with the analogous day-gap recursion, both
implemented from scratch in the validator, not reused from the solver's own
constraints.

For each check type solved in isolation, the legacy model returns an optimal,
fully covered schedule that the independent replay certifies as correct: zero
threshold violations across all four check types on
\texttt{ABCD\_near\_threshold\_test}. This is the practical evidence that the
corrected hierarchy model enforces every check type (hour-triggered A/B and
calendar-triggered C/D) without relaxation on realistic, non-adversarial
instances.

On the full mixed-hierarchy instance, the replay flags four aircraft/check
violations, of which three (aircraft~0's A and B checks, aircraft~1's B
check) are fully explained by the instance's deliberately overdue initial
state ($\Phi^A_0=27\,001>T^A_{\max}=27\,000$, similarly for $B$) -- a data
precondition violation that would also invalidate the exact-state model's own
initial condition \eqref{eq:c13b}, independent of which C13 formulation is
used. The remaining case is genuine: aircraft~2 starts with
$\Phi^A_2=26\,800<T^A_{\max}$ (not overdue), yet the legacy solution flies
enough on day~1 to reach 27\,200 minutes, exceeding the 27\,000-minute
threshold, a violation the legacy split model's own constraints do not
detect. This is a second, independently arising instance of the same
endpoint-split flaw proved in \Cref{lem:c13_split_limit} and
\Cref{tab:c13_loophole} -- found on an existing test instance under the full
hierarchy, not constructed by hand -- and it demonstrates that the flaw is
not confined to contrived corner cases: it can occur whenever the
hierarchy's aggregated $\mathrm{mega}$ indicator lets a heavier check on one
aircraft satisfy the endpoint condition for another aircraft's window in the
same solve.

\subsection{Summary of findings}

\begin{enumerate}
  \item The current runs validate execution on synthetic configurations named
    after Tables~5, 6, 10, and~11; they do not reproduce the published data or
    averages.
  \item The Constraint~(13) endpoint-split flaw of \Cref{lem:c13_split_limit}
    is confirmed computationally: all 42 real constraint rows built by
    \texttt{src/model.py} for the loophole instance are satisfied at an
    adversarial point where 1\,200 minutes are actually flown against a
    600-minute limit, while the exact-state recursion correctly rejects it.
  \item Solved in isolation, each of the four check types (A, B, C, D) is
    enforced correctly by the legacy hierarchy model on
    \texttt{ABCD\_near\_threshold\_test}: optimal, fully covered, and
    independently validated with zero violations.
  \item Under the full mixed hierarchy, the same flaw reappears
    unprompted on an existing test instance (aircraft~2 in
    \texttt{ABCD\_check\_hierarchy\_test} exceeds its A-check threshold by
    200 minutes with no violated constraint reported), showing the issue is
    not confined to hand-built corner cases.
  \item The boundary suite confirms that the legacy endpoint-split MILP
    executes on all key edge cases and is infeasible on the mixed-maintenance
    case under CPLEX; this is a separate, solver/formulation-scale question
    from the correctness results above.
  \item The heavy-instance stress test shows that, with the full CPLEX Studio
    executable, the legacy MILP solves the density-$0.5$ instances to
    formulation-level optimality.
  \item On dense cases, the legacy MILP does not return a certified solution
    for the reported horizons within the current run budget; this is a scale
    limitation of the exact solver environment, not a correctness question.
  \item The CPLEX installation available in this environment is a
    size-restricted Community/Preview edition and cannot solve any instance
    with maintenance constraints active (\texttt{CPLEX Error 1016}); the
    new Constraint~(13) and hierarchy results therefore use the open-source
    HiGHS solver, which is exact and unrestricted.
\end{enumerate}
