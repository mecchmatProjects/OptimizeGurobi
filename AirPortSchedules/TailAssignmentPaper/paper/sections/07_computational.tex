\section{Computational Study}
\label{sec:computational}
%%==========================================================================

\subsection{Implementation and environment}

All models are implemented in Python~3.10+ using the Pyomo optimisation
framework~\citep{pyomo2023} and solved with IBM ILOG CPLEX~\citep{cplex2023}.
Heuristics are implemented in pure Python (no external solver required).
All experiments were run in a Windows environment with CPLEX Studio available
on the shell path and invoked through Pyomo's \texttt{cplex} backend.
The code, instance generator, and experiment runner are publicly available at
the companion repository.

\paragraph{Comparison protocol.}
The reported methods use the same JSON instances and assignment-cost data.
They do not yet constitute a fully controlled formulation comparison: the
legacy MILP uses the endpoint-split C13 implementation, heuristic rows may be
partial assignments, and exact-state MILP runs are not included in the tables
below. Consequently, costs are compared only between solutions with equal
flight coverage, and no conclusion about the relative strength of the paper,
split, and exact-state C13 formulations is drawn from these runs.

\subsection{Instance generation}

The current generator creates deterministic synthetic instances. For
parameters $(\delta,n_p,n_d)$ it generates approximately
$\delta n_p n_d$ flights, chooses airports and times from seeded pseudo-random
distributions, and uses a stable seed for each test index. Thus $\delta$ is a
flight-count scaling parameter in this repository, not the fleet-to-minimum-
fleet ratio used by \citet{khaled2018compact}. Unless a table states otherwise,
the quick snapshots contain one generated instance per parameter cell.

\texttt{ABCD\_multi\_check\_test} & ERROR & ERROR & -- \\
\bottomrule

\end{table}

In the latest stronger run, each label produces the same profile: two optimal
targeted-instance solves, two targeted errors, and six infeasible generated
cases. This equality is expected from the shared builder and supplies no
evidence about relative formulation strength. The supported observations are:
\begin{itemize}
  \item The labelled runs produce identical outcomes on
    \texttt{ABCD\_check\_hierarchy\_test} and
    \texttt{ABCD\_near\_threshold\_test}.
  \item On the harder generated and all-checks cases, all tested variants
    hit infeasible or error outcomes under the current settings.
  \item A valid empirical comparison requires separate paper-C13,
    endpoint-split, and exact-state builders plus post-solve counter checks.
\end{itemize}

The heuristic-only comparison in \Cref{tab:heuristic_only} shows that the two
deterministic constructive methods are effectively indistinguishable on this
instance: both terminate in under a millisecond, cover seven of eight flights,
and yield the same objective value.  In contrast, the ACO heuristic explores a
larger portion of the search space and achieves a lower partial-route cost,
but this comes with reduced coverage, leaving three flights unassigned.  The
result is consistent with the draft's characterization of ACO as a more
exploratory but less stable heuristic than the deterministic constructions.

Across all methods in \Cref{tab:heu_benchmark}, the legacy MILP is the only
approach that returns a complete assignment. Its objective cannot be ranked
against the partial heuristic objectives without an explicit unassignment
penalty. The brute-force and DP
exact-search prototypes remain useful as validation scaffolding, but on this
instance they do not yet provide competitive production solutions for the full
TAP search space.

This dense suite sharpens the same qualitative conclusion as the lighter

legacy MILP reaches the practical limit of the current environment on the
denser instances: the smallest dense case is reported infeasible, whereas the
larger horizons terminate without a certificate inside the current run budget.

\subsection{Summary of findings}

\begin{enumerate}
  \item The current runs validate execution on synthetic configurations named
    after Tables~5, 6, 10, and~11; they do not reproduce the published data or
    averages.
  \item The C13-labelled runs all use the endpoint-split legacy builder and
    therefore provide no empirical comparison of paper, split, and exact-state
    formulations.
  \item The two deterministic heuristics behave almost identically on the
    bottleneck instance, but both leave one flight unassigned.
  \item Across the reported suite, ACO has lower coverage and longer runtime
    than the deterministic methods; its lower raw route cost reflects fewer
    assigned flights and is not a quality improvement.
  \item The legacy MILP returns the only complete assignment on the bottleneck
    comparison and solves it in well under one second.
  \item The boundary suite confirms that all implemented methods execute on
    the key edge cases, while the exact-search prototypes are inapplicable on
    larger instances.
  \item The heavy-instance stress test shows that the heuristics remain fast
    on larger generated cases, and with the full CPLEX Studio executable the
    legacy MILP solves the density-$0.5$ instances to formulation-level
    optimality.
  \item On dense cases, all heuristic outputs are partial and the legacy MILP
    does not return an optimal solution for the reported horizons.
  \item The brute-force and DP exact-search prototypes remain valuable for
    validation, but they are not yet competitive as production exact solvers
    for the full TAP search space.
\end{enumerate}
